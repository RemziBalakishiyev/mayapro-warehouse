## 2026-08-16

- **Multi-tenant SaaS Mərhələ 2 — abunə sistemi və platforma admin API-si** (BE#36, BE#35-in davamı). Tam təsvir: [`docs/multi-tenancy.md`](../multi-tenancy.md) §9.
  - **Platforma admini.** Yeni `UserRole.PlatformAdmin` + `PlatformAdminOnly` policy. **`TenantId` qərarı:** sütun `NOT NULL` qaldı və admin rezerv edilmiş `TenantDefaults.PlatformTenantId` (`…-0000000000ff`) id-si ilə saxlanılır — nullable etmək `TenantEntity`/query filter/unikal indeksi dəyişməyi tələb edərdi, `Guid.Empty` isə `TenantInterceptor`-un "boş = təyin edilməyib" kontraktını pozardı və boş tenant kontekstində məhz həmin sətri görünən edərdi. Rezerv id heç bir `tenancy.Tenants` sətrində yoxdur, ona görə onun altında bir dənə də biznes sətri olmur → adminin hər tenant-scoped sorğusu boş qayıdır (fail-closed), amma öz `identity.Users` sətri tapıldığı üçün `GET /api/auth/me` bypass-sız işləyir. `identity` sxemi üçün miqrasiya LAZIM GƏLMƏDİ. Seed: `PlatformAdminSeeder` — `PlatformAdmin` konfiqurasiya bölməsindən, **hər mühitdə**, idempotent, bölmə boşdursa heç nə etmir.
  - **Tenant qapısı.** `TenantGateMiddleware` `PlatformAdmin` rolunu buraxır (yeganə istisna; tenant claim-siz ADİ token hələ də 401) və mövcud tenant lookup-ının içində abunə yoxlaması edir — ikinci sorğu yoxdur, çünki `TenantInfo` artıq `ExpiresAt` daşıyır. 403 cavabları statusa görə ayrıldı: `Auth.TenantPendingApprovalForbidden` («Hesabınız təsdiq gözləyir»), `Auth.TenantBlockedForbidden` və `Auth.SubscriptionExpiredForbidden` («Abunəliyiniz bitib — əlaqə: {admin telefonu}», telefon `PlatformAdmin:Phone`-dandır). Login eyni kod/mesajları qaytarır. **Wire dəyişikliyi:** bloklanmış mağazanın login cavabı əvvəl `Auth.TenantInactiveForbidden` / «Mağaza aktiv deyil» idi — indi yalnız *tapılmayan* tenant bu cavabı alır.
  - **Qeydiyyat.** `POST /api/auth/register` (anonim) → `Tenant(PendingApproval)` + ilk Sahibkar, tək `IUnitOfWork` transaction-ında (`TenancyDbContext` bunun üçün `ITransactionalDbContext` oldu). Telefon **qlobal** yoxlanılır → təkrar 409 `Tenancy.PhoneAlreadyExists`; bu, `multi-tenancy.md` §4.1-dəki "eyni telefon iki mağazada" qalıq riskini bağlayır. Token qaytarılmır. **Rate-limit qəsdən Mərhələ 3-ə saxlandı** (sənədləşdirilib).
  - **Abunə.** `Tenant.ExpiresAt` (nullable = **müddətsiz**, heç vaxt bitmir) + `Tenant.MonthlyFee` + yeni `tenancy.SubscriptionPayments` (`TenantId, Amount, PaidAt, PeriodMonths, Note, RecordedByAdminId`); migration `AddSubscriptionFields`, **back-fill YOXDUR** — mövcud mağazalar (o cümlədən "İlk Mağaza") müddətsiz qalır, yəni işləyən quraşdırma yeniləmədən sonra özünü kilidləmir. Təsdiq: `ExpiresAt = now + N ay`; ödəniş: `ExpiresAt = max(now, mövcud ExpiresAt ?? now) + N ay`. Avto-blok **statusu dəyişmir** — `ExpiresAt` özü hökmdür, ona görə ödəniş yazılan kimi mağaza növbəti sorğuda açılır (fon işi yoxdur, yenidən login lazım deyil). Bütün tarix hesabı `Tenant` domain-indədir və "indi"ni arqument kimi alır (`IDateProvider.UtcNow`), ona görə saatsız unit testlə örtülüb.
  - **Admin endpoint-ləri** (`/api/admin/*`, hamısı `PlatformAdminOnly`): tenant siyahısı (status/axtarış filtri + billing xülasəsi), mağaza yaratma, approve/block/unblock, ödəniş yazma və tarixçəsi, statistika. `SubscriptionPayment` **qəsdən** `ITenantScoped` DEYİL: platforma səviyyəli billing qeydidir və onu tenant-scoped etmək bypass-sız olmalı modula `IgnoreQueryFilters()` gətirərdi.
  - **Bypass təhlükəsizliyi (AC-7).** Yeni `IgnoreQueryFiltersArchitectureTests` bütün `src/**/*.cs` mənbəsini oxuyur: allowlist-də olmayan `IgnoreQueryFilters(` çağırışı → test qırılır; allowlist-də olub artıq mövcud olmayan yol → test də qırılır (siyahı köhnəlmir). Allowlist 9 yoldan ibarətdir (login, qeydiyyatın telefon yoxlaması, faktura token lookup-u, 6 startup seeder) — Tenancy admin use case-lərinin bypass ehtiyacı YOXDUR.
  - Testlər: `PlatformAdminApiTests` (21 ssenari, uçdan-uca HTTP), `SubscriptionPeriodTests` (8, saatsız riyaziyyat), `PlatformAdminRoleTests` (4), arxitektura testi (3), `TenantQueryFilterCoverageTests`-ə `tenancy` sxemi üçün əsaslandırılmış allowlist. Yeni test layihəsi: `MayaPro.WarehouseApi.Modules.Tenancy.Tests`.

## 2026-08-01

- **İşçi maaş sistemi** (BE#28): `User.MonthlySalary` (`decimal(18,2)` NOT NULL DEFAULT 0, `SetMonthlySalary` metodu ilə dəyişir) + yeni `SalaryEntry` entity-si (`identity.SalaryEntries`, migration `EmployeeSalaryAndSalaryEntries`). Beş yeni endpoint: `PUT /api/employees/{id}/salary` (O), `POST`/`GET /api/employees/{id}/salary-entries` (O+M / auth), `DELETE /api/employees/{id}/salary-entries/{entryId}` (O), `GET /api/employees/salary-summary?month=` (O+M); `GET /api/employees` cavabına additiv `monthlySalary`. Wire: `type` = `"payment"` (kassadan real pul çıxır) \| `"deduction"` (yemək/yol/cərimə — yalnız işçinin hesabından tutulur), `WireFormat.SalaryEntryTypes`-a əlavə olundu. **`Date` və `Month` ayrı semantikadır**: `Date` pulun çıxdığı UTC anıdır (gün sonu/dashboard `IDateProvider.LocalDayRangeUtc` ilə ona baxır), `Month` isə `yyyy-MM` hesab ayıdır (maaş xülasəsi ona baxır) — keçən ayın maaşını bu gün ödəmək bir sətirdir. Xülasə: `remaining = monthlySalary − paidTotal − deductionTotal`, MƏNFİ ola bilər (artıq ödənilib), sətri olmayan işçi də `0/0/monthlySalary` ilə siyahıdadır. **Gün sonu inteqrasiyası**: yeni `ISalaryModule` kontraktı `IExpensesModule` ilə tam simmetrikdir — `GetDayPaymentsTotalAsync(date)` (CloseDayHandler günün xərc cəminə əlavə edir → `ExpectedCash = OpeningCash + CashSales − (xərclər + maaş ödənişləri)`) və `GetPaymentsAsync(from, to)` (DashboardCalculator `todayExpenses`-ə əlavə edir və «son bağlanışdan bəri» diapazonundan çıxır, bağlanmış gün ikinci dəfə çıxılmır). `ClosingDto` wire formatı DƏYİŞMƏYİB — maaş ödənişi mövcud `expenses` rəqəminin içinə düşür (ADR-0006); tutulmalar heç bir kassa rəqəminə düşmür. **Arxitektura dəyişikliyi (RISK-1)**: `AuthDbContext` öz connection string-indən paylaşılan `IDbConnectionFactory` bağlantısına keçdi və `ITransactionalDbContext` kimi qeydiyyatdan keçdi (`ActivityModule`/`DayEndModule` üslubu) — maaş sətri ilə activity log-unun atomik yazılması üçün şərtdir; login, `GET /api/auth/me`, startup migration və `UserSeeder` axını dəyişməyib. 400 halları: `Salary.InvalidType`, `Salary.InvalidMonth`, məbləğ ≤ 0, qeyd > 500 simvol, mənfi maaş; 404: `Auth.UserNotFound`, `Salary.EntryNotFound` (yad işçinin sətri route-dan görünmür).
- **Açıq borclar siyahısı — FIFO bölgü** (BE#21): yeni `GET /api/customers/open-debts` (auth) — bütün müştərilərin hələ bağlanmamış borc mənbələri `{items[], totalRemaining}` şəklində, ən köhnə borc əvvəldə. Mənbə = ilkin borc sətri (`source: "initialDebt"`, `description: "İlkin borc"`) və ya qalıqlı satış (`source: "sale"`, `description: "mal adı × say"`, `originalAmount` = satışın YEKUNU deyil, borc yaradan qalığı). Müştərinin ödənişləri mənbələr üzərində tarix artan sırada (FIFO) silinir; `remaining = 0` olan mənbə siyahıya düşmür; `daysOld` Asia/Baku tam günləri ilə (`IDateProvider`, ADR-0005). Hesablama sorğu anındadır — ayrıca cədvəl, miqrasiya və ya sxem dəyişikliyi YOXDUR — və müştəri sayından asılı olmayaraq dörd sorğudur (müştərilər + ilkin borclar + qruplaşdırılmış ödəniş cəmləri + yeni kontrakt metodu `ISalesModule.GetOutstandingSalesAsync`, tək round-trip; N+1 yoxdur). Bir müştərinin qalıqlarının cəmi `Customer.Debt`-ə bərabər olmalıdır: fərq exception atmır, yalnız warning kimi log-a düşür (data keyfiyyəti siqnalı). Silinmiş müştəriyə aid qalmış satış sətirləri siyahıdan çıxarılır. Ödəniş cəmi ilə işləmək ödənişləri bir-bir tətbiq etməklə eyni nəticəni verir (ödəniş heç vaxt o andakı borcdan çox ola bilmir), ona görə ödənişlər qruplaşdırılmış tək sorğu ilə oxunur.
