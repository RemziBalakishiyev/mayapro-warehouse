## 2026-08-22

- **Telefon nömrələrinin kanonik saxlanması** (BE#46). Bir nömrənin neçə cür yazıla biləcəyi indiyə qədər DB-də neçə cür saxlanırdı: `0501234567`, `+994 50 123 45 67` və `994501234567` üç ayrı sətir idi — halbuki telefon həm login identifikatorudur, həm də `IX_Users_TenantId_Phone` unikal indeksinin sütunudur. Nəticə: eyni adam iki hesab aça bilirdi, indeks isə heç birini dublikat saymırdı.
  - **Tək qayda, tək yer.** Yeni `PhoneNormalizer` (SharedKernel/Application, mövcud `Result`/`Error` pattern-i ilə, exception atmır): rəqəmlərə qədər təmizlə (yalnız ASCII `0-9`) → `0` ilə başlayan 10 rəqəm `994` + son 9 rəqəm olur → `994` ilə başlayan 12 rəqəm olduğu kimi qalır → başqa hər hal `Error.Validation` («Telefon nömrəsi düzgün formatda deyil (məs: 050 123 45 67)», `General.Validation` → 400). İki metod: `Normalize` (məcburi; boş giriş mövcud «Telefon boş ola bilməz» mesajını saxlayır) və `NormalizeOptional` (boş → `null`, yəni DB-də `NULL`, boş sətir deyil; amma dolu-oxunmayan dəyər yenə xətadır). **`501234567` (9 rəqəm) qəsdən rədd olunur** — yazılmamış başlanğıc `0`-ı təxmin etmək istifadəçinin verməmiş olduğu nömrəni uydurmaqdır. Modullardakı dağınıq `phone.Trim()` çağırışları (`TenantProvisioning`, `IdentityProvisioningContract`, `PlatformAdminSeeder`) normalizer-ə keçdi; `UserSeeder`/`SupplierSeeder` demo nömrələri də oradan keçir, ona görə seed və qayda bir-birindən ayrıla bilmir.
  - **Tətbiq nöqtələri (10).** `RegisterTenantHandler` + `CreateTenantHandler` (hər ikisi ortaq `TenantProvisioning`-dən — owner phone VƏ `Tenant.Phone`), `LoginHandler`, `IdentityProvisioningContract.PhoneExistsAsync`/`AddOwnerAsync`, `PlatformAdminSeeder`, `Create`/`UpdateCustomerHandler`, `Create`/`UpdateSupplierHandler`, `UpdateSettingsHandler`. Optional telefonlarda yoxlama sətir oxunmazdan ƏVVƏLdir, ona görə pis telefon yarımçıq redaktə qoyub getmir. Mövcud `MaximumLength(30)` qaydaları xam giriş üzərində saxlanıldı.
  - **Login köhnə formatla işləyir** (əsas uyğunluq vədi): giriş nömrəsi normallaşdırılıb axtarılır, `0501234567` / `050 123 45 67` / `+994 50 123 45 67` / `994501234567` eyni istifadəçini tapır. Oxuna bilməyən nömrə format xətası YOX, mövcud neytral `Auth.InvalidCredentials` («Telefon və ya şifrə yanlışdır») alır — iki fərqli cavab özü «bu nömrə mövcuddur/yoxdur» sızması olardı. Boş telefon köhnə 400-ünü saxlayır. BE#35-in çoxsaylı namizəd məntiqi və BE#36 tenant qapısı toxunulmadı.
  - **Qeydiyyat dublikatı kanonik dəyər üzərindədir**: mövcud `994501234567` varsa `+994 (50) 123-45-67` ilə qeydiyyat 409 `Tenancy.PhoneAlreadyExists` verir və nə `Tenant`, nə `User` sətri yaranır.
  - **Miqrasiyalar (5 modul, data-only, sxem dəyişikliyi yoxdur):** `NormalizePhoneNumbers` — `customers.Customers`, `suppliers.Suppliers`, `identity.Users`, `settings.StoreSettings`, `tenancy.Tenants`. T-SQL C# qaydasının eynisidir (rəqəm çıxarışı `Latin1_General_BIN2` altında mövqe-mövqe + `FOR XML PATH`, çünki T-SQL-də regex yoxdur). Çevrilə bilməyən dəyərlər **toxunulmur** — yalnız sayılır; hər cədvəl `RAISERROR(..., 0, 1) WITH NOWAIT` ilə bir log sətri yazır: `[BE#46] <schema>.<cədvəl>.Phone - normallasdirildi: N, cevrile bilmedi: M` (say 0 olsa da yazılır; `normallasdirildi` = faktiki dəyişən sətir sayı, ona görə təkrar icrada 0-dır). `UPDATE` yalnız dəyəri fərqlənən sətirlərə vurur → idempotentdir. `Down()` sxem baxımından təhlükəsiz no-op-dur və **data-nı geri qaytarmır** (kod şərhində açıq yazılıb): köhnə sərbəst formatlar heç yerdə saxlanmır və geri qayıtmaq aradan keçən login-ləri sındırardı.
  - **Auth miqrasiyası dublikatda DAYANIR** (ardıcıllıq qəsdəndir: əvvəl yoxlama, sonra yazma). Kanonik dəyərlər temp cədvələ hesablanır, `GROUP BY TenantId, kanonik HAVING COUNT(*) > 1` yoxlanılır və dublikat varsa `THROW` — mesajda `TenantId`, kanonik nömrə, hər `User.Id`, adı və köhnə dəyəri var; transaction geri qayıdır (bir sətir də dəyişmir) və startup uğursuz olur. Tərs sıra unique index pozuntusu ilə anlaşılmaz, izahsız xətaya gətirərdi. Fərqli mağazalarda eyni nömrə dublikat DEYİL (unikallıq tenant-scoped-dır). Əl ilə həll edildikdən sonra eyni miqrasiya təkrar icra olunur və keçir.
  - **Unikal indeks toxunulmadı** — `IX_Users_TenantId_Phone` nə silindi, nə yenidən yaradıldı, adı/sütunları eynidir; sadəcə tərkibi bir formaya gəldiyi üçün artıq kanonik dəyərləri qoruyur.
  - **Wire təsiri (bug deyil, gözlənilən nəticə):** GET/DTO cavablarında telefon indi kanonik sətirdir (`994501234567`). Sahə adları və tipləri DƏYİŞMƏYİB. Frontend `waLink()`/`phoneDigits()` onsuz da yalnız rəqəm saxlayır, ona görə `https://wa.me/994501234567` dəyişməz alınır — **frontend-də heç bir dəyişiklik edilmədi və tələb olunmur** (backend tərəfdən yoxlaması `PhoneNormalizerTests`-dədir). İnsana oxunaqlı göstərim (`+994 50 123 45 67`) ayrıca FE taskıdır.
  - Testlər: `PhoneNormalizerTests` (SharedKernel, qəlib cədvəli + idempotentlik + boş/optional davranışı + wa.me uyğunluğu), `PhoneFormatApiTests` (28 uçdan-uca ssenari: müştəri/təchizatçı/settings/qeydiyyat/admin mağazası/login), `PhoneNormalizationMigrationTests` (10 ssenari, ayrıca throwaway DB + `IMigrator`: 5 cədvəlin çevrilməsi, log sətirləri, dublikat DAYANDIRMASI və sonrakı uğurlu icra, tenant-scoped dublikat, indeks pozuntusu, ikiqat icra + `Down()`), `LoginHandlerTests`-ə köhnə format/neytral mesaj/deaktiv hesab halları.
